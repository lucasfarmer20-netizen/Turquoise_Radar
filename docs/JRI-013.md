## Backup, recovery and monitoring

Use a separate trusted private runner for hourly authenticated current-ledger
pulls. Keep Google upload credentials off the public receiver VM. This runner
must already exist or be separately costed/approved; an offline laptop does not
deliver an hourly backup guarantee. Bootstrap its empty local ledger explicitly
under the receiver's existing HMAC key, then require the live signed pull before
each backup. Never replace a newer ledger with an old snapshot.

`backup-ledger.py backup --source EXISTING_LEDGER --destination NEW_PRIVATE_DIR`
creates a consistent SQLite copy, including committed WAL state, with a checksum,
key-binding and aggregate-count manifest. `verify --destination DIRECTORY` checks
the copy. Files are 0600 and the directory 0700; missing/wrong-key/corrupt or
permissive copies fail. The tool fsyncs before success, emits no account identifiers,
and explicitly reports that the copy is **offline, not current receiver proof**.
It performs no upload, restore or activation.

Encrypt the verified directory client-side on the private runner, using an
independently recoverable key, before uploading under a unique immutable object
name to a dedicated private GCS Standard bucket in `us-west1`. Proposed bucket:
`tr-ebay-ledger-<verified-project-number>` (availability pending). Enforce uniform
bucket-level access and public-access prevention. Use a narrowly scoped backup
writer and a separate restore reader; do not grant the receiver bucket access.
Verify upload checksums and persist an aggregate success receipt. Keep the HMAC
key and encryption recovery key separately protected and recoverable; neither
belongs inside the ledger manifest or ordinary archive. OAuth credentials and
verification-token recovery need the same separate private inventory.

Proposed retention: 24 hourly, 7 daily and 4 weekly copies, with reviewed lifecycle
rules and an explicit 7-day soft-delete setting. Count retained, noncurrent and
soft-deleted bytes toward the 5 GiB-month planning budget. Verify upload/retention
permissions and actual storage during the approved setup; local-only copies do
not count as successful off-VM backups. This preparation supplies the local
verified-copy tool and the operational plan; it has not installed an hourly
scheduler or cloud uploader on any runner.

Target RPO is at most one hour **only while scheduled pulls and uploads succeed**;
RTO of four hours is a planning target requiring a recovery drill. A committed
receiver acknowledgement proves local durability, not zero loss after destruction
of the VM/disk. Events accepted after the last successful off-VM copy can be lost.
On failure, first keep workbench maintenance/restores quarantined. Preserve any
surviving receiver disk and local ledgers, verify backups/keys, and reconcile the
superset of accepted events without permitting conflicts or rollback. An old
backup alone cannot prove a complete ledger after total host loss. Do not start
it as a supposedly current authoritative receiver until that gap is reconciled;
obtain authorized eBay redelivery/support if required. The existing fresh-ledger
barrier remains mandatory before private replay or restore acceptance.

Monitor failed pulls/uploads, backup age (>90 minutes), queue growth, free disk,
service restarts, clock skew, TLS expiry and sustained 412/503 responses without
logging notification bodies, identifiers, tokens or signatures. Use existing
approved monitoring on the private runner; no paid monitoring service or cloud
logging agent is included. Perform a synthetic recovery drill before activation.
