# JRI-015 — sourcing feed and source preparation

JRI-015 is an independent development branch based on main, separate from draft
[JRI-014 / PR #26](https://github.com/lucasfarmer20-netizen/Turquoise_Radar/pull/26).
It uses the existing intake, Discovery planner, review queue and owner feedback.
No Production OAuth/Browse request, paid inference, purchase, bid, source polling
or scraping is authorized or performed by this work.

## Owner workflow

1. Open **Sourcing feed** (`/feed`). Real-data items are the default. Open review
   excludes passed, purchased, irrelevant and known-ended items; select
   **Closed / ended** or **All review states** to revisit them. Filter by source,
   review state or dataset, and sort by last-recorded time or existing evidence score.
2. Review the observed item price, Alaska shipping eligibility, delivered
   acquisition cost and next missing evidence. An observed auction price is not a
   winning bid. Unknown components stay unknown; estimates remain labeled. Non-USD
   amounts are not converted or fed into a claimed USD delivered cost.
3. Inspect exact query/correction provenance and original candidate details. Send
   an unreviewed candidate to the existing queue, or open an existing listing's
   evidence editor. Interested, Pass and False positive use the existing feedback
   endpoint and history; they perform no marketplace action.
4. Open **Prepare searches** (`/feed/prepare`). Select 1–20 phrases from the existing
   65-phrase catalog, preserving spelling, case and spaces. Saving creates a new
   **disabled** Discovery group with auction and fixed-price formats, newly-listed
   order, no price filter and omitted `auto_correct`. It does not execute anything.
5. Review that group in Discovery before enabling it. Preview the actual active
   plan: existing pattern activity, source restrictions, priorities and budgets
   still apply. Staging does not guarantee every selected phrase will be included.
   An unchanged repeated submission reuses its draft; an edited draft is never
   overwritten by resubmission.
6. For owner-managed auction and marketplace sources, use the preparation table
   to open the existing source-specific saved-search assistant. Set up alerts
   yourself where supported, then import owner-provided notifications, text or
   structured data. Selected/configured counts are owner setup records, not proof
   of a working integration or successful search yield. No source is automatically
   enabled or contacted.

## Evidence and data boundaries

The feed is a read-only projection of existing records. Multiple candidates already
linked to the same owner listing appear once; all their observations remain visible.
Unlinked candidates and manual-only listings remain separate. Matching titles do
not merge identities or sources. The canonical owner listing supplies reviewed
costs, shipping, state and feedback instead of stale candidate fields.

Fixture, sandbox and mixed provenance have separate views and counts. Mixed data
never enters the default real-data view. Real-data counts are stored items, not
verified current marketplace availability or ranking-performance evidence. Explicit
ended observations and timezone-aware item end times can mark an item ended;
otherwise availability is unknown. Auction-wide deadlines do not establish item
expiry. Query attribution remains separate from literal-match semantics, and
promotional or recommended material does not become a verified saved-search match.

No new database table, private-data copy, schema migration, background worker or
external image fetch is introduced. Feed pages are private/no-store. Existing eBay
deletion tombstones and their linked candidates are suppressed without recovering
data from original payloads or historical snapshots. Existing deletion handling,
receiver infrastructure, IAM and encrypted backups are untouched.
