## Public boundary and delivery

`radar.ebay_deletion.receiver:from_env --factory` is a **separate FastAPI app**.
It imports no workbench application, database, image store or discovery adapter.
Its only resource is `/ebay/account-deletion` (GET challenge, POST notification).
It has no public docs, queue download, status, file or private processing routes.
The deployment archive includes only the receiver/maintenance package, not the
workbench. The proposed host must not contain workbench data or maker libraries.

GET returns SHA-256 of `challenge_code + verificationToken + exact configured
HTTPS endpoint`, as lowercase hexadecimal JSON `challengeResponse`. The token is
32–80 URL-safe characters. Missing, repeated or invalid challenges fail safely;
the request Host header never determines the hashed endpoint. An arbitrary valid
challenge cannot be recognized as incorrect locally: eBay detects a wrong token
or URL by comparing the digest. Tests cover both different-token/URL mismatches.

POST limits streamed bodies to 32 KiB and 10 seconds, signature headers to 4 KiB,
and accepts uncompressed JSON only. It rejects duplicate JSON keys and unsupported
topics/schema versions. It Base64-decodes `X-EBAY-SIGNATURE`, validates the key ID,
retrieves the key only from the fixed official Production Notification API, and
verifies ECDSA/SHA1 over `JSON.stringify(parsed message)` with DER/Base64 signature.
`verify.cjs` uses Node's native crypto and the same algorithm/serialization as the
official eBay Node SDK; no unofficial eBay endpoint is involved. The PEM encoding
is normalized. The retrieved algorithm/digest must match; input cannot choose an
arbitrary verification algorithm or remote key URL. Node is a required runtime.

Only after successful verification and a committed SQLite write does POST return
204. Duplicate notification IDs with identical account hashes are harmless, even
when delivery-attempt metadata differs. A conflicting account payload is rejected.
Storage, key retrieval, OAuth or verifier availability failures return a fixed 503;
invalid signatures/notifications return a fixed 412. No raw body, account ID,
description, signature, token, credential or authorization header is logged.
Disable proxy/access/request tracing as in the service configuration. Apply host
request limits/rate controls before exposing the endpoint; a malformed/key-ID flood
must not become unbounded OAuth traffic. Concurrency is limited to 16, one process.

The receiver holds application OAuth tokens **in memory** and refreshes before
expiry; keys are cached for one hour, at most 32 IDs. It makes no Browse calls and
does not modify Browse enablement, approval or per-run consent. Minimum access:
client-credentials application token with `https://api.ebay.com/oauth/api_scope`
and GET `/commerce/notification/v1/public_key/{public_key_id}`. No user consent,
checkout scopes or Notification subscription-management scope is needed for portal
setup/key lookup. OAuth failure is not retried automatically by this code. A
subsequent notification delivery can attempt verification again.

**Bootstrap dependency:** the disabled keyset may reject application-token minting
until portal validation enables it. Challenge verification needs no OAuth, but
signed notification verification does. Confirm token/key access after the portal
accepts the endpoint; if eBay keeps it disabled, resolve that ordering with eBay
Developer Support. Do not bypass signatures or acknowledge discarded messages.

Events are stored outside the workbench on the receiver's persistent encrypted
volume, SQLite synchronous FULL, mode 0600. Accepted identifiers and notification
IDs become domain-separated HMAC-SHA256 values under an independent high-entropy
secret. Plain identifiers and raw messages are discarded. This minimal private
ledger remains append-only for restore prevention; it is pseudonymous data, not
anonymous public telemetry. Keep its HMAC key and protected backup recoverable;
never rotate/delete it without a reviewed migration. Receipts contain only event
HMAC, asset-path hash, status, count and timestamp. Workbench downtime does not lose
accepted events. Delivery acknowledgement is distinct from completed removal.

### Offline removal and recovery

Use `deploy/ebay-deletion/inventory.example.json` as a schema example, not an
actual owner inventory. Set `inventory_complete=true` only after tracing all
copies, exports, files and off-host snapshots. Each linked photo needs an entry
under `photo_reviews` keyed `maker_photos:<id>` or `vision_photos:<id>`:
`kind: independent` plus reviewed `evidence`, or `kind: seller_copy` plus reviewed
`evidence` and its exact `path`. Source-copy content must match the DB's content
hash and `<id>.png`. Missing/mismatched provenance blocks removal. Independent
reference/evaluation photos must never be classified as seller copies by association.

Stop the workbench, all import/export processes and all DB users. Replay is an
explicit destructive maintenance operation, not part of setup/startup by default:

```bash
# After authenticated ledger synchronization and reviewed inventory, ONLY when authorized:
.venv/bin/python -m radar.ebay_deletion.cli replay \
  --manifest /PRIVATE/inventory.json --queue /PRIVATE/deletion-ledger.db \
  --require-fresh-ledger --apply
```

One BEGIN IMMEDIATE transaction handles each DB. Receipts follow data commit and
VACUUM; a crash before a receipt is safe to replay. Reviewed seller-file unlink
precedes SQL commit, so interrupted removal retains the matching account record
for retry; already missing files are harmless. Stop in-flight RESERVED/SENT vision
runs before processing; preserve budget amounts and held-cost status. A blocked
asset does not make the event complete. Nonzero CLI exit keeps the workbench and
restores quarantined. A NO_MATCH result retains the ledger for later copies.

SQLite secure-delete/VACUUM removes content from current logical DB/free pages;
it does **not** prove erasure from SSD blocks, provider snapshots, filesystem
journals, replicas or archives. Use encrypted storage and reviewed key destruction
or verified sanitized rebuilds for those copies, preserving unrelated owner data
in a verified replacement. Never declare compliance based only on deleting a row
or adding a restore tombstone. Mixed archives are a deliberate unresolved manual
review path, not automatically exempt and not silently deleted wholesale.

Restore only into a **new quarantined path** included in the inventory:

```bash
.venv/bin/python -m radar.ebay_deletion.cli restore \
  --source /PRIVATE/old-backup.db --destination /PRIVATE/quarantine/restored.db \
  --manifest /PRIVATE/restore-inventory.json --queue /PRIVATE/deletion-ledger.db \
  --require-fresh-ledger --apply
```

The restore verifies integrity then replays all retained deletion events; any
coverage hold prevents acceptance. Before reopening a workbench or any restored
copy, pull a fresh receiver ledger and run this gate. A direct unmanaged `cp`
or bypassed startup command is outside this guarantee and must be forbidden by
operator permissions/runbooks. This repository does not intercept arbitrary
filesystem copies. Do not reconnect imports/discovery until affected aliases and
external-copy handling are resolved.

### Private connection, monitoring and shutdown

The public receiver exposes no pull API. Give a dedicated SSH key a forced command
running `snapshot-queue.py`, with read-only queue access, no forwarding, no PTY and
no interactive shell. Pin the receiver's SSH host key. It emits a consistent
SQLite snapshot via stdlib backup, including only hashed ledger/receipts. On the
private machine (commands proposed, not run against a remote host in this task):

```bash
ssh -T -o StrictHostKeyChecking=yes receiver-ledger > /PRIVATE/incoming-ledger.db
.venv/bin/python -m radar.ebay_deletion.sync \
  /PRIVATE/incoming-ledger.db /PRIVATE/deletion-ledger.db
# Then use replay --require-fresh-ledger --apply before opening workbench/restores.
```

`EBAY_DELETION_HMAC_KEY` must be the same protected key locally. Sync checks its
fingerprint, merges events and refuses a remote rollback/conflicting event;
it never replaces the local append-only ledger. The fresh-ledger gate requires a
successful sync within 15 minutes. An old queue snapshot cannot silently undo
prior removal evidence. Test the SSH permissions and restricted command on the
actual chosen host before activation; no SSH host/key exists yet.

Operate a manual daily ledger pull/removal review while private processing is
available, and replay before reopening after downtime. Escalate overdue pending
removals; a queue retained while the workbench is offline is not a completed
removal. Use `python -m radar.ebay_deletion.cli status --queue /PRIVATE/deletion-ledger.db`
for aggregate counts without identifiers. Inspect service health, disk capacity, pending/blocked receipts, last
successful pull and eBay alert email. Service restarts recover the durable queue;
SQLite full/disk/key-access failures produce non-success responses for delivery
retry. Configure an owner-approved host monitor before launch; none was provisioned.
Rate limit inbound requests at the host firewall/edge. Never log request bodies,
header values or challenge query strings. Restrict diagnostic logs and ledger access.

Shutdown: stop acceptance deliberately, preserve the ledger/key and pending work,
notify the owner and update the registered destination before retiring a host.
Do not keep returning 204 while stopped processing or discard queues. eBay's
current guide describes retries, a down-endpoint alert after 24 hours of failed
acknowledgement and a 30-day remediation window; those are not a data-retention
exemption or a reason to defer an accepted removal.
