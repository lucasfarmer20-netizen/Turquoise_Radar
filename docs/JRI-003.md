# JRI-003 — Local hallmark similarity and targeted growth

## Outcome and limits

A CPU-only retrieval prototype now indexes **22 reviewed mark images/crops across
17 reference records**: seven whole-jewelry records and ten isolated shop-mark
references. It accepts a local private image and returns candidate references with
source links, attributed maker/shop, mark description, legibility, cosine score and
uncertainty. It does not authenticate authorship, cultural identity, gemstones or
metal, and it never changes financial or historical evidence.

The targeted catalogued-object count reached **20**, with two views per object.
Ten additional standalone mark references are counted separately. The earlier
20-image Cleveland collection remains preserved but is not counted as Southwestern
coverage. The store now has 50 item/reference records and 70 downloaded image
assets overall: 20 Cleveland images, 40 targeted object views and ten standalone
mark references. Crops and synthetic query derivatives are not new acquisitions.

This is a single-source, low-resolution evaluation milestone, not a representative
independent hallmark benchmark. No independent owner query photograph was supplied.
Similarity performance does not approve LoRA or any other training.

## Local prototype

The optional `similarity` extra installs pinned CPU PyTorch/Torchvision packages
on Linux x86-64. All pre-existing locked dependency versions are unchanged. Ordinary
application setup needs no embedding dependencies and has no implicit model fetch.

```bash
uv sync --frozen --extra similarity
.venv/bin/python -m radar.references.similarity fetch-model
.venv/bin/python -m radar.references.similarity index --include-internal-fair-use
.venv/bin/python -m radar.references.similarity query data/private-hallmark.jpg \
  --top-k 5 --html data/private-hallmark-results.html
```

Use `--root` and `--weights` **before** the subcommand to select another private
store or pinned model file. `fetch-model` is the only network operation in this
module: it downloads public weights from the official PyTorch host, without
sending any reference/query image. Index, query and evaluate run locally with no
inference API, model hosting, remote hub execution or automatic download. A
missing store/model is an error; setup never initializes a replacement database.

The model is Torchvision's open-weight
[ResNet-18 ImageNet1K V1](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.resnet18.html),
using its 512-dimensional average-pool representation. Torchvision code is
[BSD-3-Clause](https://github.com/pytorch/vision/blob/v0.24.1/LICENSE); this does not
confer rights in reference photographs or the model's original training corpus.
The weights are loaded locally with `weights_only=True`, checked against the full
SHA-256 `f37072fd47e89c5e827621c5baffa7500819f7896bbacec160b1a16c560e07ec`.
The official source is `https://download.pytorch.org/models/resnet18-f37072fd.pth`.

Preprocessing validates bytes, applies orientation and strips metadata using the
existing pixel pipeline, then letterboxes the complete mark to 224 pixels and
applies ImageNet normalization. It deliberately avoids a center crop that could
remove inscription characters. This differs from the standard classifier recipe
and is included in the index revision. Small marks are resized only for model
input, never presented as newly recovered photographic detail. No OCR, rotation
invariance or hallmark-specific accuracy is claimed.

Only photograph-backed mark records from currently eligible, unexcluded sources,
items, assets and crops are indexed. Explicit reviewed mark crops replace the
whole decorative photo for that parent asset. Reported-only inscriptions are not
visual retrieval references. Both current source review and historical image
rights snapshots gate use; internal fair use requires the explicit index flag.
A metadata/eligibility change invalidates the index until it is rebuilt, while
file corruption fails closed. Multiple views from one item are collapsed in query
results so they do not crowd out other candidate objects.

The private JSON index is under `data/jri/similarity/`. The query accepts a bounded
local JPEG/PNG/WebP file, not a URL. Optional HTML results embed only scrubbed local
pixels, escape source/query metadata, disable remote resources/scripts with CSP,
and refuse to overwrite an existing file. Source links require a deliberate click;
no gallery resource loads when the report opens. Reports are private historical
snapshots: manually remove exported copies when their supporting rights/evidence
are withdrawn. Scores are cosine similarities, not probabilities or calibrated
acceptance thresholds. Private query photos, indexes and reports never go to GitHub.

## Retrieval evaluation

Private cases declare positive and negative reference IDs, label evidence and query
independence. Exact-self image hashes are excluded, query results are collapsed by
item, and family holdouts additionally exclude the query's reference record.
Three private DIFFICULT_NEGATIVE pairs compare visually confusable Bell versus
Atkinson, Running Bear and Maisels marks. These label a retrieval task under
uncertain source attribution, not independently verified maker/material truth.

```bash
.venv/bin/python -m radar.references.similarity evaluate \
  data/jri/jri003/evaluation-cases.json
```

| Query stratum | Cases | Correct first result | Matching reference in top 5 |
| --- | ---: | ---: | ---: |
| Source-attributed shop-family holdout | 6 | 3/6 (50%) | 4/6 (66.7%) |
| Repeated source-composited inset | 8 | 7/8 (87.5%) | 8/8 (100%) |
| Synthetic brightness/JPEG perturbation | 17 | 17/17 (100%) | 17/17 (100%) |
| Independent owner capture | 0 | Not measured | Not measured |

Family holdouts produced **23 different-family results among 30 returned top-five
slots** (7/30 matched the labelled family). Repeated-inset checks had 32 nonmatching
slots; synthetic checks had 68. These counts are ranked distractors, not false
accepts from an authentication decision: the prototype always returns neighbours
and has no calibrated accept/reject threshold. Per-case judged precision@5,
recall@5, unjudged results and false-family counts are retained privately.

The model is good at reproducing near-identical inputs but weak at generalizing
across shop-mark variants. One repeated inset also ranked a wrong item first.
Shared watermarks, backgrounds, resizing and source-composited insets can inflate
apparent performance. No independent-capture precision, unknown-maker rejection
rate or deployment false-accept rate is established. The next useful evaluation
needs independent owner photographs and more independently supported difficult
negatives, not LoRA approval based on the synthetic scores.

## Repeatable private persistence across Cloud tasks

The CLI creates **self-contained**, SHA-256-manifested, SQLite-consistent snapshot
volumes. It is independent of the old overlay chain and includes source reviews,
observations, original/normalized media, crops, local index and private reports.
Weights remain separately reproducible public downloads outside the dataset root.
Only ignored `data/` or locations outside the repository are allowed for outputs.

```bash
.venv/bin/python -m radar.references.persistence verify
.venv/bin/python -m radar.references.persistence backup data/backups/jri003-final
# Retain the printed manifest SHA-256 separately with the private backup links.
.venv/bin/python -m radar.references.persistence --root data/jri-restored restore \
  data/backups/jri003-final --manifest-sha256 THE_RECORDED_MANIFEST_SHA256
```

The established personal private backup Page (linked in the owner’s task report)
is the cross-task persistence destination. Confirm owner-only sharing before
uploading every new volume and `backup.json`; keep the manifest digest with the
links. The current session verifies a complete restore into a separate directory
before publishing backup links. Do not use the older ten-image or overlay backups
when the new self-contained snapshot is available.

In a new Cloud task, first inspect/verify the active private tree. If it is already
complete, retain it. If absent, download **all** volumes and `backup.json` from the
private Page and attach them to the task, or place them in an ignored local backup
directory. Downloads may gain filename suffixes: rename the index to `backup.json` and
the volumes to `part-001.zip` through `part-005.zip` before restore.
Current Page tools cannot read ZIP bytes directly; downloadable personal
attachments plus reattachment are the handoff, not an automatic mount or public
storage service. Downloaded attachments can then be materialized by the task's file
tool and verified using the recorded manifest digest. Missing/corrupt volumes stop
restoration; an existing tree is never overwritten and no empty replacement is
initialized. Restores validate archive/payload hashes, paths, bounds, symlinks,
duplicate/missing entries, SQLite integrity, foreign keys and media hashes before
selecting the new directory. Preserve old snapshots until the new restore passes.

No paid storage account, public bucket, cloud deployment, automatic gallery crawl,
Anthropic call, training, financial/budget change or historical-run change is part
of this implementation. The PR requires review and is not merged automatically.
