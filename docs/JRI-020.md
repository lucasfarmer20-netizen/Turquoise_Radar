# JRI-020 — offline fresh-pilot qualification

This is a synthetic-only one-shot command, not a production launcher. It creates
an exclusively new private directory and exercises the existing Browse adapter,
nonce/HMAC synchronization and deletion replay. It does not read environment
credentials, make network requests, launch an application or authorize real data.
The old JRI-019 pilot and the separate 27-item email application are never opened.
No previous uncommitted JRI-020 controller was available in this checkout.

## Run locally

Use a new path with an existing parent. Do not point at any existing application:

```bash
.venv/bin/python -m radar.discovery.offline_pilot prepare \
  --workspace /tmp/SYNTHETIC-jri020-username
.venv/bin/python -m radar.discovery.offline_pilot execute \
  --workspace /tmp/SYNTHETIC-jri020-username --approved-preview DIGEST_FROM_PREPARE
```

The default username-only case must exit 2 and remain QUARANTINED. To exercise
sufficient synthetic identity evidence separately, prepare a different new path
with `--scenario stable-fixture`. This inserts **hypothetical** stable seller IDs
in mock responses. It is not evidence that actual Browse summaries return those
fields or that real sellers have reviewed mappings. A successful run reports
`QUALIFIED_SYNTHETIC_ONLY`, with `display_authorized=false`; it never permits real
execution. The public fixture key is not an operational credential. The fixture
receiver/local ledgers are never substitutes for an existing real ledger.

## Fixed scope and gates

The exact original order is:

1. `blue stone ring`
2. `silver ring with blue stone`
3. `sterling jewelry lot`
4. `mixed jewelry lot`

The real adapter constructs EBAY_US / US 99669 context, newlyListed, both buying
formats, omitted auto_correct, one page/query, three results/page, and twelve
observations maximum including duplicates and invalid records. Timeout is 15s,
request spacing 1s and retry limit 2, as in JRI-019. This is four logical searches,
not a promise of four HTTP attempts during failures. The controller caps mock
OAuth attempts at 3 and mock Browse attempts at 12 (15 total). The normal mock
result is one OAuth + four Browse exchanges, twelve observations/eight items.
US/99669 context does not establish item-specific Alaska delivery eligibility.

No image requests are made. A future image-only continuation requires its own
exact fresh-reference preview and preserved original image bounds (at most eight
attempts, one/reference, no retries/redirects); the old frozen-cohort image runner
is not repurposed or supplied replacement records.

Preparation creates only an empty migrated database with the exact disabled
search plan, a complete cohort inventory, fixture ledgers and a digest-bound
preview. Existing directories, symlinks, unknown copies and changed inventories
are rejected. The sole source-data asset is pilot.db, including original responses,
observations and query history. No raw payloads are written to receipts, exports
or files outside it. Control files contain fixed configuration, aggregate results
and digests; fixture ledgers contain synthetic HMAC identifiers. Any future image,
export or database copy must extend the inventory before creation. This scoped
inventory does not claim to discover arbitrary external copies made by an operator.

Every deletion gate obtains a different challenge and uses the existing real
maintenance verifier and replay; only the receiver transport is replaced locally.
Key binding, signature, nonce, time window and ledger continuity are not bypassed.
The three gates are before collection, after collection and before synthetic
qualification. Missing/invalid proof or REVIEW_* results retain quarantine.
Even an empty event set cannot qualify username-only candidate identity.

An exclusive fsynced authorization marker is created before any mock OAuth/Browse
attempt. A workspace lock prevents concurrent runs. A marker survives interruption;
no resume or retry can redispatch that workspace. Discovery is disabled on normal
and handled-failure exit. A hard process kill can leave its database setting enabled,
but the consumed marker blocks controller reuse and no application is started.
The workspace must remain quarantined; this is not a production serving barrier.

## What this demonstrates and what still blocks live use

Username-only evidence yields UNMAPPED/REVIEW_IDENTITY under existing deletion
rules, even against an unrelated stable-ID notification. The controller preserves
that hold. Empty-ledger testing also fails closed. Exact stable-ID fixtures can
pass, and matching later notifications sanitize their records before qualification.
No real seller is asserted to have supported stable identity evidence. A real beta
needs evidence accepted by the existing identity rules, including compatibility
with actual notification identifier types; inventing aliases or treating different
usernames as proof of non-match is not permitted.

The owner reports successful pinned IAP receiver/runner checks, ledger integrity,
and a fresh encrypted backup with 8,944 events and zero processing receipts. That
supports receiver/backup operation, not deletion coverage of this new database.
The saved current_receiver_proof=false is expected; an old receipt is not fresh
maintenance authority. The restore-reader ciphertext test remains inconclusive.

The next live decision is a **single bounded integration placement**, not a new
receiver or infrastructure rebuild: establish where the new quarantined cohort
and every copy will live, and bind its actual inventory to the existing authorized
maintenance context without exporting keys or widening the reader identity.
An owner-operated job in that context is a candidate, not a verified capability.
Its available paths, permissions, eBay credential delivery and ability to maintain
all copies are not established here. A live launcher/serving barrier must require
that coverage and current proof, never accept these fixtures or a saved success
receipt, and retain per-run approval and marketplace policy gates.

Do not collect live data until that placement and supported identity coverage are
resolved. Do not reuse the removed deployer, create a replacement ledger, export
HMAC credentials, modify private hosts or add infrastructure to make this offline
result look live-ready. Restore-reader troubleshooting is separate unless the
chosen operation actually requires backup restoration.

## Offline detail hydration proposal

The [official Browse OpenAPI schema](https://developer.ebay.com/api-docs/master/buy/browse/openapi/3/buy_browse_v1_oas3.json)
documents getItem's ADDITIONAL_SELLER_DETAILS field group and describes
seller.userId as stable across username changes. The [notification topic schema](https://developer.ebay.com/develop/api/buy/notification_events)
describes marketplace-deletion data.userId as an immutable public user ID. This
is a plausible documented identity path, not a verified cross-API worked example
or proof that this Production keyset returns the field. No live call was made.

A new, separately selected `--scenario hydrated-fixture` evaluates that path with
mock search summaries containing only usernames and mock getItem responses with
explicit synthetic userIds. The default username scenario and original search
limits remain unchanged. Preparation binds the changed detail proposal into its
preview digest; an existing workspace/approval is not reused.

The wrapper buffers each search page in memory, hydrates each distinct exact item
ID once, and validates matching item ID and exact seller username before returning
anything to the existing persistence code. Missing IDs, seller/item mismatch,
unexpected status or a failed detail request stops subsequent acquisition; that
page's seller data is not retained. Already completed, fully hydrated pages remain
quarantined if a later page fails. This conservative username comparison may reject
legitimate intervening username changes; it never guesses a mapping.

The original summary seller fields are unchanged. A typed, versioned identity
receipt is added to each original observation: operation, requested field group,
exact item ID, aware detail timestamp, summary digest, and returned seller userId
and username. Arbitrary detail descriptions/contact information are not retained.
The detail timestamp is identity provenance, not refreshed quote/availability
proof. Duplicate items share an in-memory detail lookup but retain their separate
query observations and summary bindings. Every receipt explicitly retains
production_validation=UNVERIFIED.

Existing deletion code already traverses nested seller identities. Synthetic
qualification demonstrates matching notification userId sanitizing the hydrated
candidate and all its original observations; no deletion matcher, alias rule,
ledger gate or old record is changed. A detail ID cannot excuse incompatible or
ambiguous notification evidence: existing REVIEW_* holds still apply. The
controller never sets display_authorized true, including after successful hydration.
