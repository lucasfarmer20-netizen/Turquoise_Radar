# JRI-005: likely maker identification and owner review

Open **Identify jewelry** (`/identify`) in the private Turquoise Radar app. A clear
match to one permitted published reference is enough to present a useful maker
candidate. Independent corroboration is optional research context, never a gate
for these candidates. The owner makes the identification and buying decisions.

## Use the workflow

1. Start a jewelry research case, optionally from a workbench listing. Upload full
   jewelry views and/or hallmark photographs. Listing details and URLs stay as
   context; URLs are not fetched and seller wording is not silently treated as a
   visible hallmark transcription.
2. Drag a rectangle around a mark, or enter crop coordinates. The app saves a new
   private crop and selects it for comparison. Uploads are byte-validated JPEG,
   PNG or WebP, with metadata removed from processing copies. Six images per upload,
   10 MB each, 40 MB total; at most 20 views/crops per case.
3. Choose a hallmark photograph and add whatever lettering, pictorial symbols and
   construction clues you can actually see. Lettering and construction observations
   are owner supplied; this release does **not** add automatic OCR or a general
   jewelry-description model. Local ResNet-18 supplies visual retrieval against the
   existing eligible index without an API call.
4. Review up to five ranked maker/shop candidates. Each shows a descriptive match
   strength, specific agreements and discrepancies, the strongest reference first,
   additional references, and original citations. Hougart citations retain fifth
   edition and printed page numbers. Eligible existing local images and private
   photographed book pages are viewable; external-only images remain links.
5. **Confirm likely maker**, **Reject candidate**, or **Further research**, with your
   reason. You can separately correct a transcription or suggest another maker.
   Rerun the search to apply corrections. Published claims and original searches
   remain unchanged. A correction resets any previous likely-maker acceptance until
   you review it again.
6. Continue in the linked workbench, or explicitly add the case to it. Missing
   costs stay unknown. Search recorded comparable-sale notes by maker, select actual
   recorded comparables, and calculate a maker-based comparison scenario. The app
   shows the selected sale range, net profit and maximum item-price calculation
   using the existing Decimal finance engine and cost/fee evidence.

Maker scenarios are **CONDITIONAL** until the owner accepts that candidate. Changing
the owner decision, listing inputs or fee/buying preferences flags an old scenario
for reconsideration or recalculation. Each scenario retains its listing, preferences
and comparable snapshots. Scenarios
do not overwrite listing finances, certify material, confirm shipping, record a
purchase or pass decision, or turn a source claim into authenticated evidence. The
existing workbench remains the place to record the owner's final buying decision.

## Matching and owner memory

The new ranking policy (`jri005-owner-likely-maker-v1`) combines distinctive
lettering, explicit aliases/name text, selected pictorial descriptions, local image
retrieval and supporting construction terms. It is separate from the frozen
JRI-004 benchmark and research-corroboration classifications. Internal ordering
points are heuristics; no probability or authentication confidence is displayed.

Clear complete lettering can yield a **Strong lettering match** from a single book
entry. Worn/partial readings, short shared initials, pictorial leads and visual-only
leads retain their qualifications. Purity/material text alone, a blank/low-contrast
crop, or broad construction/style alone cannot identify a maker. Unknown source
identities are shown as unresolved marks instead of inventing maker names. A failed
or unavailable local model leaves text/description search usable with a visible
explanation; model files are never downloaded automatically.

Identical reported maker-name labels can group references for display; the directory
identities are not merged. Generational qualifiers and initials remain distinct.
Variants are inspectable individually and shared/reused stamp notes remain visible.
Repeated references do not multiply the ranking score as if they were independent.

Owner decisions are append-only records associated with a case and immutable search.
Same-case rejections leave the active ranking after another search, while retaining
history and a reconsider action. Prior decisions on other cases are shown only for
the same normalized distinguishing text/symbol signature or exact processed-photo
hash. Their aggregate influence is a small bounded tie-breaker; rejecting a maker
on another piece cannot erase a strong published match. Owner-only maker corrections
are explicitly labeled as owner leads with no published reference attached. There
is no feedback training, benchmark insertion, or reference-index mutation.

## Run locally and preserve private data

Use the existing private application database, then open `/identify`:

```bash
VISION_PROVIDER=fixture VISION_LIVE_ENABLED=false \
  .venv/bin/uvicorn radar.main:app --host 127.0.0.1 --port 8000
```

`RADAR_DATABASE_URL` continues to select the workbench database. Source/model paths
can be configured with `JRI_DIRECTORY_DIR` (default `data/jri-directory`),
`JRI_LIBRARY_DIR` (`data/jri`) and `JRI_MODEL_PATH`
(`data/jri-models/resnet18-f37072fd.pth`). Existing pinned ResNet weights and the
optional similarity dependencies are required for photo retrieval; see JRI-003
setup. Text search works without them. Do not rebuild the frozen index to add cases.

`JRI_OWNER_IMAGE_DIR` defaults to `<application-db-stem>-maker-images` beside the
application database. Owner image storage cannot overlap the reference directory,
library or historical evaluation directory. It must be private/ignored storage,
never public static files. Image URLs resolve only known photo/reference IDs, check
current eligibility and content hashes, and return private noncached responses.
Identification pages allow only same-origin image loading. The app retains its
existing private/local deployment and same-origin mutation guard; no new public
hosting or account system is introduced.

Application migration 6 adds `maker_cases`, `maker_photos`, `maker_runs`,
`maker_decisions`, and `maker_scenarios`. It creates the existing migration backup
before upgrading a populated database and preserves all prior tables/rows. The JRI
reference databases are read-only in this workflow. A missing directory produces a
restore message; it is never replaced with an empty reference library.

Back up **both** the application SQLite database (using a consistent SQLite backup)
and its maker-image directory to preserve cases and owner actions across cloud
tasks. They are separate from the existing seven-volume JRI reference handoff.
Case JSON export is an inspectable research record, not a self-contained image or
application restore package. Retain the reference handoff and pinned model weights
as before. Never commit private databases, photos, book scans, reports or decisions.

## Validation and limits

The latest JRI-004C backup restored successfully: 571 hash-verified payloads across
seven volumes, 641 searchable records, 120 Hougart entries, 16 evaluation originals
and the frozen 22-image index. The active SQLite schemas/rows matched the verified
restore; SQLite backup container bytes can differ from the live databases. The final
preservation check confirmed all 36 historical table contents remained unchanged.

Validation on 2026-10-31: **700 tests passed**, including 28 identification tests;
Ruff lint, formatting and whitespace checks passed. The suite emits the existing
Starlette/AnyIO deprecation warning.

Offline tests cover single-source candidates, UNKNOWN, conflicting/partial letters,
shared initials, negative symbol descriptions, bounded owner feedback, corrections,
upload/crop validation, rights restrictions, source/benchmark isolation, migrations,
stale/cross-case decisions, and conditional comparable scenarios without financial
mutation. A Chromium check exercised the real private directory and pinned local
ResNet using a clearly synthetic uploaded hallmark. It covered crop selection,
candidate review, confirm/reject, workbench linkage, conditional valuation, a
single-Hougart candidate and its private page, and a narrow mobile viewport. It made
zero external browser requests and reported no page errors.

This validates a working owner workflow, **not** an accuracy improvement on the 16
owner photographs. Those photographs and their historical benchmark were not
rerun or changed. Visual coverage remains 22 indexed images; many directory records
support text/manual reference research only. More independent owner photographs
and careful owner review are still needed to measure recognition performance.
