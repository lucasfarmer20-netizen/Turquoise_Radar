# JRI-001 — Private jewelry reference aggregation

This feature is a local CLI and private reference database, separate from the
existing application database. It does not change Haiku requests, VisionResult,
financial calculations, purchasing recommendations, owner evidence or billing.
There are no training, inference-provider, hosting or public-serving calls.

## Source policy

The owner's JRI-001 policy supersedes the earlier blanket image-license proposal:

- `OPEN_ACCESS`: official API or individually supported reuse basis. The adapters
  check image-level rights, not just metadata rights.
- `INTERNAL_FAIR_USE`: source-specific owner review of copyright rationale,
  contractual restrictions and permitted technical access. This is not a license
  or a finding of legal clearance. A manually reviewed URL manifest can collect
  from such a source without requiring individual training licenses.
- `REFERENCE_ONLY`: useful external research; no image collection.
- `BLOCKED`: collection prohibited by the reviewed restrictions/access method.

Unknown/restricted source methods are not treated as fair use automatically.
Network-policy failure is a paused transport state, not a copyright finding.
Each source stores its terms URL, review date, access method, restrictions,
provenance, eligibility, contact status and request interval. Reviews expire after
90 days and must be refreshed explicitly; prior versions remain in `source_reviews`.
Initialization never resets exclusions or replaces owner reviews.

## Quick start

From the checkout, using the existing environment:

```bash
.venv/bin/python -m radar.references.cli init
.venv/bin/python -m radar.references.cli sources
.venv/bin/python -m radar.references.cli collect cma --query jewelry --max-items 300 --max-images 400 --live
.venv/bin/python -m radar.references.cli report
```

Repeat the same collect command to resume. Increase bounds or start additional
queries as needed; there is no global few-hundred-image cap. Query examples:
`bracelet`, `ring`, `pendant`, `brooch`, `turquoise`, `silver jewelry`. Relevance
requires jewelry terminology in the title/object type and excludes artwork types
such as portraits and paintings. This is a conservative lexical filter, not a
claim of expert jewelry classification; inspect retrieved examples before training.
Museum coverage may be broader than Southwestern jewelry, and search can miss
relevant objects with ambiguous titles.

Supported batch controls: `--max-items`, `--max-images`, `--max-pages`,
`--page-size` (1–50), `--max-requests`, `--max-bytes`. The last defaults to 1 GiB
per invocation. Defaults are bounds, not automatic collection schedules. Each
invocation requires `--live`; initializing, searching and exporting never fetch.
Source and media hosts need to be explicitly reachable through the normal proxy:

```text
openaccess-api.clevelandart.org
openaccess-cdn.clevelandart.org
collectionapi.metmuseum.org
images.metmuseum.org
api.artic.edu
www.artic.edu
commons.wikimedia.org
upload.wikimedia.org
```

## Durability and networking

The private store is `data/jri/references.db` by default. `--root` selects a private
location under ignored `data/` or outside the checkout; public static/source
locations are refused. It uses foreign keys, an ordered transactional schema
version and an OS writer lock. It rejects unrelated/newer SQLite databases rather
than replacing them. No application database migration is required.

Each source/query has a durable cursor. A page and its pending item queue commit
atomically before the cursor advances. Images commit individually; interrupted
items resume without transferring completed views again. OS locks release on
process exit. Stale RUNNING batches are marked interrupted on a later invocation.

The client identifies itself, follows the configured proxy/CA, sends no source
credentials, checks robots before collection, observes crawl-delay/request-rate
and source spacing, bounds decoded response bytes and validates every redirect
host. Robots errors fail closed; a missing robots file (404) permits access under
the reviewed terms. Robots redirects currently pause for review rather than being
followed automatically. Rate-limit/server errors pause the batch; Retry-After
sets a durable cooldown. There are no automatic retries, CAPTCHA handling, hidden
API discovery, login or proxy-bypass paths. A manual later invocation resumes.

Safe event logs contain fixed categories, local identifiers, HTTP status and
counts. Remote exception messages, response bodies, image bytes and credentials
are never copied into logs. Source metadata is stored privately as evidence,
not embedded into diagnostic messages. Network HTTP debugging is suppressed.

## Images and provenance

PNG/JPEG/WEBP are decoded and verified, including actual dimensions and corruption
checks. Animated, tiny, over-25-megapixel or over-20-MiB files are rejected. Originals
remain byte-for-byte private. Normalized RGB PNG derivatives apply EXIF orientation,
remove metadata and fit within 1600 pixels without upscaling. Both hashes and
processing versions are retained. Crops refer to the normalized coordinate space.

Exact duplicates share content-addressed storage while retaining each item's
image/provenance/rights record. Near duplicates use a 64-bit difference hash and
indexed byte bands, with Hamming distance <=4. They are review candidates, not
proof of identical jewelry; they are not silently removed. Conservative grouping
keeps them together in evaluation splits. Highly similar backgrounds may create
false positives; visually different crops may escape this detector. No embedding
model has been downloaded; a private embeddings table is reserved for later work.

CMA imports the available web image. Met and AIC retain multiple available views.
Commons records are file-level references; multiple files depicting one physical
object require review/grouping before evaluation. Unknown view orientation remains
`UNSPECIFIED`; the collector does not guess front/back or manufacture hallmarks.

## Evidence, hallmarks and research filters

Item metadata contains stable source/external IDs, page URL, title, object type,
artist candidates, photos and source assertions. Assertions separately store:
`field`, `value`, `origin`, `status`, `confidence`, evidence URL/photo/document,
`test_method`, `tester`, `tested_on`, `scope`, `supersedes`, and whether the assertion
is observable from a photograph. Imported source claims start ATTRIBUTED/UNKNOWN.

Recommended field vocabulary includes `maker_attribution`, `shop_attribution`,
`trading_post`, `attribution_qualifier`, `reported_marks`, `stone_identification`,
`stone_treatment`, `construction`, `setting`, `estimated_era`, `documented_date`,
`stated_dimensions`, `ring_size`, `stated_weight`, `measured_weight`, `metal_test`,
`provenance`, `research_signal`, `maker_group`, `split_group`. Unknown fields remain
absent. No extraction guesses weights, tests, era or marks from an image.

Origins distinguish museum/gallery/seller/community catalog, owner inspection,
owner-reported testing, independent testing and model predictions. Acid, XRF,
assay, other and unknown testing methods are distinct; method and sampled scope
must not be generalized into an unsupported whole-object purity claim. DOCUMENTED
requires an evidence reference, not just confidence; references and reviewer
judgment still need human checking. Model predictions cannot be DOCUMENTED.

A separate mark table holds literal transcription, pictorial description,
legibility, source/item/photo or crop, candidate makers and mark variants. Matching
a mark does not authenticate authorship or cultural origin. Partial transcriptions
remain partial and reported-only marks are distinguished from photographed marks.

```bash
.venv/bin/python -m radar.references.cli search 'STERLING' --source cma
.venv/bin/python -m radar.references.cli search 'GERMAN SILVER'
.venv/bin/python -m radar.references.cli search 'artist name'
.venv/bin/python -m radar.references.cli add-evidence data/private-assertion.json
.venv/bin/python -m radar.references.cli add-mark data/private-mark.json
.venv/bin/python -m radar.references.cli crop ASSET_ID 0 0 200 200
```

Search covers artist, mark transcription, pictorial descriptions, source and
assertions. STERLING/925/950/980, TAXCO/MEXICO, ALPACA/GERMAN SILVER and plating can
be stored/searched as reported inscriptions. No inscription equals an assay.
`research_signal` supports future Native-premium/import-review, Mexican-silver and
alpaca/German-silver review labels. These are research annotations only: this
feature does not alter financial filters or infer base metal from foreign origin.

Corrections are appended with `supersedes`; old assertions are retained. Existing
Run #7 owner evidence is not imported, reclassified or changed automatically.

## Reviewed gallery manifests

Register a source using `review-source data/private-source-review.json`. Supply
all `Source` fields, including approved hosts, REVIEWED_MANIFEST access, current
terms date, restrictions and the source-specific rationale. For INTERNAL_FAIR_USE,
`rights_claim` must remain `NOT_LEGALLY_CLEARED`. Image licenses are recorded as
`UNLICENSED_INTERNAL_FAIR_USE`, not rewritten into a purported open license.

```bash
.venv/bin/python -m radar.references.cli import-manifest SOURCE_ID data/reviewed-items.jsonl --max-items 100 --max-images 300 --live
```

Each input line follows the `Item` schema. The manifest is hash-bound and resumes
by byte offset through the same durable queue; changing it creates a new stream,
while existing items/images remain deduplicated. It downloads only the explicit
reviewed image URLs. It never traverses arbitrary gallery links or uses hidden APIs.

## Removal and export

```bash
.venv/bin/python -m radar.references.cli exclude --source SOURCE_ID
.venv/bin/python -m radar.references.cli exclude --item ITEM_ID
.venv/bin/python -m radar.references.cli exclude --asset ASSET_ID
.venv/bin/python -m radar.references.cli purge
.venv/bin/python -m radar.references.cli export jri-v001 --split-mode artist
```

Exclusion immediately prevents collection/export/search of the selected scope
and invalidates earlier exports. `purge` removes excluded/unreferenced media,
embeddings and export files while retaining provenance tombstones. Shared blobs
remain when an eligible item still references them. Generated files are not a
public library. Copies made outside this store are not automatically recalled.

Exports contain versioned `examples.jsonl`, `pairs.jsonl` and a hashed manifest,
with local private image/crop paths, rights snapshots, full assertion history,
current evidence-qualified labels and separate model predictions. Use
`--include-internal-fair-use` explicitly to include that classification in a local
export. Neither option authorizes a provider upload or training job.
An image's original fair-use classification still requires this option after a
later source review; changing the registry never retroactively licenses old images.

`add-pair data/private-pair.json` records reviewed POSITIVE, DIFFICULT_NEGATIVE or
UNCERTAIN relationships for maker-candidate, mark-variant, construction or material
research tasks. It requires rationale, evidence references and a reviewer; no
counterfeit/base-metal negatives are invented. Only pairs wholly within one split
are exported. Pair labels need quality review before supervised training.

All views/crops and exact/near duplicates are grouped. Artist-aware mode also
unions shared normalized artist names, mark candidates and explicit `maker_group`
assertions. Manual `split_group` assertions connect mixed-lot/co-photographed
items and cross-source identities. Names are not an authority file: resolve aliases
and collisions before trusting maker-disjoint results. Unknown makers are not
invented. Groups deterministically receive 80/10/10 buckets; small datasets may
have empty splits. Splits are frozen per export; corrections can change grouping
in a later version, so compare models on the same frozen held-out version.

Only DOCUMENTED, explicitly photograph-observable, non-model assertions enter
`visual_training_targets`. A source's maker/material claim or hidden assay is not
silently converted into an image-only answer. Exports remain `training_ready=false`
until manual rights/evidence/leakage review. This is a provider-neutral preparation
format, not a completed Together upload or a claim that LoRA accuracy has improved.

## JRI-001 validation and live limitation

The actual initial batch attempted all four public APIs with bounds of 300 items,
400 images and 1,200 requests per source. All stopped at their first robots request
with NETWORK_PROXY_BLOCK. The workspace's enforced egress list does not contain
any required collection host. No rights or server prohibition was bypassed.

Actual result: **0 discovered items, 0 stored images, 0 rejected records,
0 duplicates**, across all four sources. Relevance cannot be evaluated without
retrieved records. Four paused batches/checkpoints are in the actual private JRI
store; the private ingestion report is `data/jri/ingestion-report.json`.

Adapters are validated against synthetic official-response shapes. Live API/schema,
robots and CDN conformance remain unverified because of the network restriction.
Do not substitute the synthetic test records for actual collection counts.

Offline checks cover resumable pagination, partial multi-view items, interruption,
rights gates, robots/rate/redirect/byte limits, exact and near duplicates, reviewed
fair-use imports, correction history, private storage, removal and split leakage.
Seven successive synthetic batches store 350 item/image references with no global
cap. The full existing application suite is run alongside these regressions.
